# Спецификация: Система-команда для TripTrek

## Задача

Ден один ведёт TripTrek — и прод, и разработку, и продвижение. Ему нужна система,
которая заменяет команду: принимает идею или задачу прямо в чате, ведёт её по всем
этапам (обсуждение → сильные/слабые стороны → спека → план → реализация → ревью →
релиз → измерение), следит за отзывами и слабыми местами, готовит маркетинговые
материалы — и при этом ничего не делает с продом, кроме чтения.

## Решение

**Система «Команда» живёт внутри репозитория** в папке `team/` — единый источник
истины: роли, жизненный цикл, шаблоны, политики, скрипты джобов. Из источника
скрипт `team/sync.mjs` генерирует платформенные точки запуска ролей для Claude Code
(`.claude/agents/`), Copilot (`.github/agents/`) и Kimi (`.agents/skills/`) —
три копии никогда не правятся руками и не расходятся.

**Конвейер:** Ден пишет задачу сообщением в чат (R13). Координатор (основной агент
диалога) регистрирует её файлом в `team/inbox/`, определяет роль по
`team/lifecycle.md`, передаёт задачу **отдельному субагенту этой роли** и ведёт её
по этапам конвейера, спрашивая его только в важных развилках (R02): одобрение
спеки/плана перед реализацией, любые действия наружу или в прод.

**Шесть ролей** (R11): Стратег (идеи, сильные/слабые стороны — R03), Архитектор
(спека, план, ADR — R04), Инженер (реализация — R05), Ревьюер (код-ревью и аудит
слабых мест — R07, R09), Рост (маркетинг: стратегия продвижения, контент-план,
черновики постов — R06), Поддержка (отзывы, черновики ответов, аналитика текстов —
R08, R10).

**Входные материалы Роста:** стратегия продвижения — документ `team/strategy.md`,
который Рост готовит первым и пересматривает по мере данных; контент-план недели
выводится из неё. Исходники для стратегии: архивные бриф и спека по привлечению
(`docs/archive/ai-team-v1/`, свежие, сегодняшние), SMM-активы владельца
(tiktok-assets), живые профили TikTok/YouTube/Instagram из политики доступа.

**Три джобы по расписанию** (R15i): дайджест отзывов — ежедневно вечером; аудит
слабых мест — еженедельно; контент-план — по понедельникам. Результаты — файлами
в `team/inbox/<джоба>/` + сообщение в чат. Наружу — ничего: ни постов, ни ответов
пользователям, ни писем (политика из v1 сохраняется).

**Прод — только чтение** (R12): скрипт `team/jobs/fetch-feedback.mjs` ходит по
SSH-алиасу `triptrek` → `docker exec triptrek-db psql` с read-only запросами
(транзакция `READ ONLY`) к таблицам `Feedback`/`FeedbackMessage` и складывает
JSON в `team/inbox/feedback/`. Изменения на проде — только по отдельному явному
запросу владельца («менять только по запросу»).

**Существующая v1 «AI team» архивируется** (R16i): `.claude/agents/triptrek-*`,
`.github/agents/triptrek-*`, `.claude/skills/triptrek-team/`, `docs/ai-team/` →
`docs/archive/ai-team-v1/`. Контент `data-access.md` и `readonly-production-access.md`
переезжает в `team/policies/` в обновлённом виде (SSH-алиас `triptrek`, не `prod`);
бриф и спека по привлечению остаются в архиве как входные материалы для роли Роста.

## Истории

| # | Метка | История | Приёмка |
|---|-------|---------|---------|
| 1 | R01 | Как владелец, я открываю `team/README.md` и вижу, как устроена команда, какие роли есть и как запустить любую | по README можно начать работу без вопросов |
| 2 | R02 | Система спрашивает меня в важных развилках — и не спрашивает по мелочам | в lifecycle и каждой роли явно перечислены точки вопросов (одобрение спеки/плана, действия наружу, прод) |
| 3 | R03 | Я пишу идею в чат — Стратег разбирает её: проблема, аудитория, сильные/слабые стороны, риски, гипотезы, метрики успеха | шаблон idea-brief заполнен по шаблону; разбор ложится в `team/inbox/ideas/` |
| 4 | R04 | Архитектор превращает одобренную идею в спеку и план тасков с зависимостями, ADR — при смене соглашений | шаблоны spec/ticket; ADR по формату docs/adr |
| 5 | R05 | Инженер выполняет только одобренный таск: код, тесты, доки тем же коммитом | правило «доки тем же коммитом» из AGENTS.md сохранено в роли |
| 6 | R06 | Рост ведёт стратегию продвижения и готовит из неё контент-план недели и черновики постов под TikTok/Shorts/Instagram | стратегия — `team/strategy.md`; контент-план — файлом в `team/inbox/content/`; публикация остаётся за мной |
| 7 | R07 | Ревьюер независимо проверяет каждое изменение до приёмки | роль запрещает ревьюеру править проверяемое |
| 8 | R08 | Поддержка каждый вечер собирает новые отзывы из прода и готовит черновики ответов | дайджест в `team/inbox/feedback/`; отправляю ответы я сам |
| 9 | R09 | Ревьюер раз в неделю проверяет слабые места: код, зависимости, тексты интерфейса, доступность | чек-лист аудита; результат — файлом в `team/inbox/audit/` |
| 10 | R10 | Поддержка анализирует тексты: отзывы (темы, тональность, частота) и тексты приложения/постов | раздел в роли Поддержки; «остальное» из брифа не раскрыто — система позволяет добавить позже |
| 11 | R12 | Любой доступ к проду — read-only через SSH `triptrek`, psql в транзакции READ ONLY | в политике и в скрипте; нарушение = стоп и вопрос |
| 12 | R13 | Я пишу задачу в чат — координатор определяет роль, передаёт её отдельному субагенту роли и ведёт по этапам | регламент в lifecycle.md; регистрация файлом в inbox; исполняет субагент роли, не координатор |
| 13 | R14i | Правлю роль один раз в `team/roles/` — `bun team/sync.mjs` обновляет все платформы | sync перезаписывает сгенерированное, есть проверка расхождения |
| 14 | R15i | Три джобы работают по расписанию без моего участия | runbook `team/jobs/README.md`; сами джобы заводит оркестратор при сдаче |
| 15 | R16i | v1 заархивирована, ничего ценного не потеряно | архив в git; политики доступа переехали в team/policies |

Проработка (deep) — ключевые решения, мои, как разработчика:

- **R01.1 (первый запуск):** `team/README.md` содержит «начни отсюда» — пример диалога с командой.
- **R08.1 (пустой дайджест):** новых отзывов нет — джоба молчит в чат и пишет файл только при наличии нового.
- **R11.1 (сбой SSH/прода):** скрипт не может подключиться — фиксирует ошибку в файле и сообщает; без ретраев в обход и без смены конфигурации.
- **R12.1 (граница чтения):** скрипт принимает только SELECT-запросы из своего кода; любая новая выборка — правка скрипта с ревью, не параметр командной строки.
- **R13.1 (неоднозначная задача):** координатор не уверен в роли — спрашивает одну строку, не угадывает.
- **R15i.1 (часы):** расписания — вечер Минска; точные минуты вне «круглых» значений.
- **R02.1:** полный список «важных развилок» фиксирован в lifecycle.md, чтобы не спорить каждый раз.

## Решения по реализации

- **Источник истины — Markdown в `team/`**: роли `team/roles/*.md` с YAML-frontmatter (name, description, платформенные поля). Скрипт `team/sync.mjs` (bun, без зависимостей) рендерит три формата по картам frontmatter — форматы зафиксированы в `interfaces.md` (сняты с существующих файлов v1).
- **Скрипт отзывов** — `team/jobs/fetch-feedback.mjs` (bun): `ssh triptrek "docker exec triptrek-db psql -U triptrek -d triptrek -c 'BEGIN READ ONLY; …'"` → JSON → Markdown-дайджест. Обезличивание: в файлы не попадают email/имена сверх того, что нужно для черновика ответа; сырые выгрузки в git не коммитятся (`.gitignore`: `team/inbox/feedback/raw/`).
- **Джобы** — Kimi Work «крон-задачи» (local_conversation) в проекте, созданные выключенными; runbook в `team/jobs/README.md` — как включить/изменить. Расписание: дайджест ежедневно 21:xx, аудит — среда, контент-план — понедельник.
- **Архивация** — через `git mv`, чтобы история файлов v1 сохранилась.
- Тесты: sync.mjs покрывается smoke-проверкой `bun team/sync.mjs --check` (расхождение → exit 1) — она же в `bun run lint` не встраивается, запускается в CI-стиле вручную и джобой аудита.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R06 — конкурентный анализ и платное продвижение | владелец (раунд 1): вне рамок v1 |
| Отправка ответов пользователям, постов, писем системой | действия наружу — всегда за владельцем (его же правило из v1 и брифа) |
| Автономные агенты, просыпающиеся от файлов в очереди | платформа так не умеет; вход — чат и джобы по расписанию (подтверждено раундом 2) |
| Read-only пользователь PostgreSQL и SSH-профиль с ограниченными правами | план из v1 (readonly-production-access.md) требует изменений на проде — только по отдельному запросу владельца; v1 работает через root с дисциплиной READ ONLY |
