# План безопасного read-only доступа к прод-воронке

- Статус: одноразовая агрегатная проверка выполнена 05.11.2026 по прямому указанию
  владельца; настройки и данные на проде не менялись. Постоянный ограниченный доступ не
  настроен.
- Цель постоянного доступа: проверять агрегированные шаги привлечения TripTrek без
  передачи агенту пользовательских записей и без технической возможности менять прод.
- Реализация доступа требует отдельного одобрения владельца после просмотра этого плана.

## Результат одноразовой проверки

- Подключение выполнено по настроенному SSH-алиасу `prod` к VPS; host key проверялся
  строго. Первый вызов по публичному hostname был остановлен из-за отсутствующего
  доверенного host key и не использовался с обходом проверки.
- Выполнены только агрегатные `SELECT` внутри PostgreSQL-транзакций `READ ONLY`, окно
  26.10–03.11.2026. Время БД — UTC.
- Результаты: 3 регистрации и 3 поездки (26.10 — по одной; 02.11 UTC — по две);
  при сдвиге UTC+3 это 26.10, 02.11 и 03.11. Одна запись места создана 26.10; новых
  записей участников с ролью не-владельца за период нет.
- Идентификаторы, email, имена, поездки, места и иные пользовательские поля не
  выбирались. Запрос не связывает место с конкретной регистрацией/поездкой и не
  атрибутирует пользователей рекламным каналам.
- Использовался root SSH, права которого технически не ограничены чтением. Несмотря на
  отсутствие изменений, этот способ не подходит для регулярного доступа; дальнейшие
  проверки — только через отдельную ограниченную роль и согласованные агрегатные views.

## Что подтверждено кодом

- Прод — Docker Compose на одном VPS; база `triptrek-db` не публикует порт наружу.
  Приложение подключается к Postgres от имени `triptrek` через `DATABASE_URL`.
- В репозитории есть инструкции для административного SSH, но отдельного ограниченного
  read-only профиля нет. Docker-доступ на сервере даёт широкие права и не считается
  read-only.
- `User` хранит email, bcrypt-хеш пароля, пользовательские ИИ-ключи и другие данные.
  `Trip`/`Place` содержат названия поездок/мест, бюджеты и координаты. Не выдавать
  аналитическому агенту прямой `SELECT` по этим таблицам.
- Для агрегатов по времени есть даты создания пользователя/поездки/места и дата
  присоединения участника. Публичных `utm_*`/`yclid` полей в схеме нет; значит, БД сейчас
  не может надёжно связать пользователя с Яндекс.Директом или VK.
- В `GET /api/admin/stats` есть агрегаты, но также последние имена, email и названия
  поездок. Этот ответ целиком нельзя передавать агенту.
- В Метрике подключён счётчик и есть цель `signup`; цель первого места и дальнейшие
  события совместного использования в найденных вызовах пока отсутствуют.
- Создание поездки идёт как минимум через `POST /api/limits` (текущий экран) и
  `POST /api/trips`; место создаётся через `POST /api/places` и `/api/places/batch`.
  Приглашение принимается через `/api/trips/join`. Любой будущий подсчёт должен учитывать
  все пути создания и считать первое место на поездку один раз.

## Рекомендуемый минимальный вариант

1. **Сначала без прод-доступа:** использовать сообщённые владельцем агрегаты Метрики и
   рекламных кабинетов. Для точных источников попросить экспорт сводки по датам/каналам,
   без user-level данных.
2. **Согласовать воронку:** регистрация → поездка создана → первое место добавлено
   (ранняя активация) → попутчик присоединился (совместная ценность). Для кампании
   фиксировать период, расходы и атрибуцию отдельно по платформам/валютам.
3. **Сначала устранить пробел атрибуции:** цели Метрики должны отправляться после
   успешных действий, а не до них. Для БД использовать только совокупные количества по
   дням/периоду; не пытаться связывать конкретные аккаунты с рекламой, пока согласованно
   не появится безопасный способ атрибуции.
4. **Подготовить агрегатные представления:** только для нужной воронки, например
   количества регистраций, созданных поездок, поездок с первым пользовательским местом
   и принятых приглашений по дате. Не возвращать идентификаторы и поля
   пользователя/поездки/места. Сейчас нельзя надёжно отличить созданное пользователем
   место от предзаполненного шаблоном/импортом: сначала нужен маркер происхождения или
   отдельный activation-event. До этого отчёт может показывать только общий показатель
   «поездка содержит место» с явным ограничением. Создание view в production — изменение
   схемы; сначала подготовить и проверить миграцию на локальной копии и получить отдельное
   одобрение.
5. **Выдать отдельную роль БД:** роль для аналитики получает `CONNECT`, нужный `USAGE`
   и `SELECT` только на согласованные агрегатные view; никакого `SELECT` на таблицы,
   `INSERT`/`UPDATE`/`DELETE`, DDL, административных прав или доступа через app-user.
   Ограничить время запроса, число подключений и срок действия/ротации учётных данных.
6. **Ограничить сетевой путь:** сейчас Postgres не публикует порт хоста. Если выбран
   туннель, сначала согласовать и проверить bind только на loopback (например,
   `127.0.0.1:5433`), не открывать Postgres наружу. SSH-профиль — отдельный аккаунт
   без shell, TTY, Docker group и sudo; разрешён только local port-forward на этот
   loopback-порт, а ключ не даёт интерактивный root-доступ. Хранить DB-секрет только в
   защищённом окружении, не в репозитории и не в чате.
7. **Атрибуция:** БД не хранит `utm_*`/`yclid`, поэтому view не сможет разделить
   Яндекс.Директ и VK. Источник/кампанию сначала анализировать в Метрике; для
   сопоставления с продуктовой активацией позже отдельно спроектировать отправку целей
   `trip_created`, `first_user_place_added` и `invite_accepted` после успешных действий.
   Это потребует изменения кода и отдельного одобрения реализации.
8. **Логи — только если нужны:** сейчас для проверки воронки они не нужны. Если позже
   потребуется проверка ошибок, передавать только заранее обезличенную сводку по
   дате/роуту/коду; отбрасывать message, stack, headers, IP, URL-query, email и payload.
   Если редактирование не гарантируется, не подключать логи и попросить владельца
   передать проверенные агрегаты вручную.
9. **Проверить ограничения до первого использования:** подтвердить, что роль не читает
   базовые таблицы, а любые INSERT/UPDATE/DELETE/DDL невозможны; порт БД недоступен
   публично; SSH-профиль не выполняет произвольные команды. Сверить JSON только с
   согласованными агрегатными полями, записать запрошенный период и отключить доступ,
   когда он больше не нужен.

Технически этот вариант всё равно добавляет пользователя/правила доступа и скрипт на VPS,
то есть меняет конфигурацию безопасности прод-сервера, хотя не меняет пользовательские
данные. Ничего из этого не выполнять без отдельного подтверждения владельца. Не добавлять
ключи, пароли, hostnames, реальные логи или выгрузки в git.
