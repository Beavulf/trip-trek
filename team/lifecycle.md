# Жизненный цикл задачи

Конвейер, по которому координатор ведёт каждую задачу. Этапы можно сжимать для
мелких задач, но ворота одобрения не пропускаются.

## Этапы

`idea → discovery → spec → plan → approved → implementation → review → accepted → release-ready → measured`

1. **Идея (idea).** Владелец пишет задачу сообщением в чат. Координатор дословно
   фиксирует формулировку и требования — ничего не теряется при обсуждении.
2. **Разбор (discovery).** Стратег разбирает идею по шаблону
   [templates/idea-brief.md](templates/idea-brief.md): проблема, аудитория,
   сильные/слабые стороны, альтернативы, риски, гипотезы, метрики успеха.
   Результат — файлом в `team/inbox/ideas/`.
3. **Спецификация (spec).** Архитектор изучает релевантный код по карте `AGENTS.md`
   и готовит спеку по [templates/spec.md](templates/spec.md): сценарии, нецели,
   ошибки и пустые состояния, данные/API, критерии приёмки.
4. **План (plan).** Архитектор разбивает работу на таски по
   [templates/ticket.md](templates/ticket.md): файлы, зависимости, проверки,
   назначенная роль. Решение, меняющее соглашения, оформляется ADR в `docs/adr/`
   до реализации.
5. **Одобрение (approved).** Обязательный стоп-гейт: спеку и план показывают
   владельцу. Согласие на обсуждение не является согласием на реализацию.
6. **Реализация (implementation).** Инженер выполняет одобренные таски: код по
   рецептам `AGENTS.md`, тесты, документация тем же коммитом.
7. **Ревью (review).** Ревьюер независимо проверяет изменения против критериев
   приёмки; править проверяемое он не может.
8. **Приёмка (accepted).** Координатор сверяет критерии, проверки и документацию.
   Невыполненные проверки называются по имени с остаточным риском.
9. **Подготовка релиза (release-ready).** Чек-лист релиза, риски и план отката,
   черновик анонса — по [templates/release.md](templates/release.md). Деплой,
   merge и публикации выполняет владелец.
10. **Измерение (measured).** После согласованного периода — разбор метрик и
    отзывов: Поддержка готовит разбор по
    [templates/feedback-analysis.md](templates/feedback-analysis.md), Рост —
    выводы для стратегии.

## Ворота одобрения: когда система спрашивает владельца

Полный и закрытый список «важных развилок». Всё остальное команда решает сама.

1. **Спека и план перед реализацией** — продуктовый код не меняется до явного
   одобрения.
2. **Любое действие наружу** — посты, ответы пользователям, письма, публикации,
   изменения в рекламных кабинетах. Система готовит только черновики.
3. **Любое изменение на проде** — код, данные, конфигурация, миграции. Чтение
   прода — только по [policies/prod-readonly.md](policies/prod-readonly.md);
   «менять только по запросу».
4. **Смена архитектурных соглашений** — сначала ADR и одобрение, потом код.
5. **Существенное расширение объёма** текущей задачи — новый scope оформляется
   отдельным таском и одобряется, а не добавляется незаметно.
6. **Неоднозначная задача** — координатор не уверен, какая роль нужна, и задаёт
   один вопрос одной строкой, а не угадывает.

Внутри этапов владельца не дёргают по мелочам: вопросы группируются, задаются
только те, чьи ответы меняют решение, по возможности — с вариантами и
рекомендованным вариантом.

## Как координатор ведёт задачу

- Каждая задача регистрируется файлом в `team/inbox/` (идеи — `ideas/`, результаты
  джобов — в свои папки). Исполняет работу отдельный субагент роли, не координатор.
- Роль определяется по этапу: идея → Стратег, спека/план → Архитектор,
  реализация → Инженер, проверка → Ревьюер, продвижение → Рост, отзывы → Поддержка.
- Ответ владельца, меняющий цель или границы, обновляет бриф/спеку/таски — работа
  по устаревшему плану не продолжается.
- Итог каждого этапа видим: обновлённый документ, список решений или
  сформулированный следующий вопрос.

## Джобы по расписанию

Три регулярные джобы работают без участия владельца: ежедневный дайджест отзывов,
еженедельный аудит слабых мест, контент-план по понедельникам. Результаты — файлами
в `team/inbox/<джоба>/`. Расписание и управление — в runbook `team/jobs/README.md`.
