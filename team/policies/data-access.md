# Доступ команды к данным

Политика обязательна для всех ролей и джобов. Обновлена из архивной версии v1
(`docs/archive/ai-team-v1/docs/data-access.md`): рабочий SSH-алиас — `triptrek`.

## Источники

| Источник | Наличие в проекте / разрешение | Рабочий доступ |
|---|---|---|
| Яндекс.Метрика | Счётчик и отправка целей из клиентского кода (`src/lib/metrika.ts`) | Кабинет и выгрузки агенту не предоставлены; анализ — по обезличенным сводкам от владельца |
| Отзывы и обращения | API, админ-интерфейс, таблицы `Feedback`/`FeedbackMessage` в PostgreSQL | Ежедневный дайджест от джобы `team/jobs/fetch-feedback.mjs` (read-only); сырые выгрузки в git не коммитятся |
| PostgreSQL на проде | Используется приложением | Только чтение по SSH-алиасу `triptrek`: `docker exec triptrek-db psql`, `SELECT` в транзакции `READ ONLY`. Порядок — в [prod-readonly.md](prod-readonly.md) |
| Серверные логи | Приложение на VPS | Рабочий доступ не настроен. Не передавать агенту SSH-ключи, env-файлы или неотфильтрованные логи |
| TikTok, YouTube Shorts, Instagram | Публичные профили: [TikTok](https://www.tiktok.com/@trip_trek_app), [YouTube Shorts](https://www.youtube.com/@TripTrekTeam), [Instagram](https://www.instagram.com/triptrek_app/) | Только просмотр публичного содержимого; не входить в аккаунты и не публиковать |
| Почта | triptrek.team@gmail.com | Только контактный ориентир. Доступа к ящику нет; агент может подготовить черновик письма, но не отправлять его |

## Правила

- **Прод — только чтение; менять — только по запросу.** Любое изменение или
  удаление данных, SQL кроме `SELECT`, изменение конфигурации или настроек —
  стоп и отдельный явный запрос владельца на конкретное действие.
- «Только чтение» обеспечивается дисциплиной: все запросы к прод-базе выполняются
  в транзакции `READ ONLY`. Root SSH технически не ограничен чтением — план
  настройки настоящей read-only роли описан в
  [prod-readonly.md](prod-readonly.md) и выполняется только по отдельному
  одобрению владельца.
- Не использовать и не выводить production-секреты, токены, пароли, cookie,
  адреса пользователей, содержимое личных поездок, фото, push-подписки или полный
  текст переписки без отдельного обоснования и согласованной процедуры.
- Для продуктовой аналитики предпочитать агрегаты, диапазоны дат и минимальные
  выборки. Не пытаться идентифицировать конкретных пользователей и не собирать
  лишние поля.
- Перед передачей обратной связи на анализ удалить email, имена,
  ссылки-приглашения, токены, точные координаты, имена поездок и другие
  идентификаторы. Скриншоты проверять на личные данные до передачи.
- Логи и выгрузки могут содержать персональные данные и секреты. Сначала
  отфильтровать и обезличить локально; исходные дампы не загружать в сторонние
  сервисы и не коммитить в git.
- Отправка сообщений, публикация постов, изменения кампаний и любые действия
  наружу не входят в полномочия ролей — только черновики для владельца.

## Что нужно для нового источника данных

1. Сформулировать вопросы и метрики, а не запрашивать «всю базу».
2. Выбрать минимальный источник: агрегированный экспорт, ограниченное представление
   или заранее очищенная выборка.
3. Новые выборки из прода — правкой кода джобы с ревью, не параметром запуска.
4. Проверить на небольшой обезличенной выборке; задокументировать поля, период
   и лимиты.
5. Временные выгрузки удалять после анализа; в отчётах — выводы и
   неопределённость, а не персональные данные.
