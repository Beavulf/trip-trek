# Read-only доступ к продy

Обновлённая версия плана из архивного
`docs/archive/ai-team-v1/docs/readonly-production-access.md`: рабочий SSH-алиас —
`triptrek` (в v1 фигурировал `prod`).

## Статус

- Рабочий канал чтения: джоба `team/jobs/fetch-feedback.mjs` — `ssh triptrek` →
  `docker exec triptrek-db psql -U triptrek -d triptrek`, запросы `SELECT` внутри
  транзакции `READ ONLY`. Запросы зашиты в коде джобы; новые выборки — правкой
  кода с ревью, не параметром запуска.
- SSH-доступ — root-профиль, технически не ограниченный чтением. Дисциплина
  `READ ONLY` обязательна; сбой подключения — фиксируем и сообщаем, без ретраев
  в обход и без смены конфигурации.
- **Любое изменение на проде — только по отдельному явному запросу владельца.**
- Постоянный ограниченный доступ (отдельная read-only роль БД, узкий SSH-профиль)
  не настроен; план ниже выполняется только после одобрения владельца.

## Что подтверждено кодом

- Прод — Docker Compose на одном VPS; контейнер базы `triptrek-db` не публикует
  порт наружу. Приложение подключается к Postgres от имени `triptrek` через
  `DATABASE_URL`.
- Docker-доступ на сервере даёт широкие права и не считается read-only.
- `User` хранит email, bcrypt-хеш пароля, пользовательские ИИ-ключи и другие
  данные. `Trip`/`Place` содержат названия, бюджеты и координаты. Аналитическим
  ролям прямой `SELECT` по этим таблицам не нужен.
- В `GET /api/admin/stats` есть агрегаты, но также последние имена, email и
  названия поездок — этот ответ целиком нельзя передавать агенту.
- В схеме нет `utm_*`/`yclid`: база не связывает пользователя с рекламным
  каналом; атрибуция анализируется в Метрике по сводкам владельца.

## План ограниченного доступа (по одобрению владельца)

1. Сначала без прод-доступа: агрегаты Метрики и рекламных кабинетов, которые
   передаёт владелец, без user-level данных.
2. Согласовать воронку: регистрация → поездка создана → первое место добавлено
   (ранняя активация) → попутчик присоединился.
3. Подготовить агрегатные представления (только количества по датам, без
   идентификаторов и пользовательских полей). Создание view — изменение схемы
   прода: сначала миграция на локальной копии и отдельное одобрение.
4. Выдать отдельную роль БД: `CONNECT`, `USAGE` и `SELECT` только на
   согласованные агрегатные view; никаких прав на базовые таблицы, записи, DDL
   или доступа через app-user. Ограничить время запроса, число подключений и
   срок действия учётных данных.
5. Ограничить сетевой путь: если выбран туннель — bind только на loopback
   (например, `127.0.0.1:5433`), не открывая Postgres наружу. Отдельный
   SSH-профиль без shell, TTY, Docker group и sudo; только local port-forward.
   Секреты — в защищённом окружении, не в репозитории и не в чате.
6. Логи — только при необходимости и только обезличенные сводки по дате/роуту/
   коду; без message, stack, headers, IP, URL-query, email и payload.
7. До первого использования проверить ограничения: роль не читает базовые таблицы,
   запись и DDL невозможны, порт БД недоступен публично, SSH-профиль не выполняет
   произвольные команды.

Технически этот план меняет конфигурацию безопасности прод-сервера, хотя и не
трогает пользовательские данные. Ничего из него не выполнять без отдельного
подтверждения владельца. Ключи, пароли, hostnames, реальные логи и выгрузки в git
не добавлять.
